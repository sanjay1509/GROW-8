# ADR 0007: Store uploaded files on a local Docker volume, behind a storage interface

- **Status:** accepted
- **Date:** 2026-11-15

## Context

Resume upload is GROW8's first file upload, and work-submission attachments (`submission_attachment`) will follow. The project's conventions already keep files outside MySQL, with only metadata and a storage key in the database, but the storage backend was an open question. The options were:

- **A local Docker volume** mounted into the API container.
- **An S3-compatible server in compose.** MinIO was the usual choice, but its community edition stopped publishing images in fall 2025 and was archived in February 2026. SeaweedFS and Garage are the remaining candidates.
- **BLOBs in MySQL.** This breaks §8 and bloats the database and its backups.

Only the API reads or writes files: the consumer services never need them. There is one API container, files are small (a resume is at most a few MB), and the only deployment target documented so far is Docker.

## Decision

1. **Files live on a named Docker volume, `file_storage`, mounted into the `api` service at `/app/storage`.** The path comes from a new env var, `FILE_STORAGE_DIR` (default `/app/storage`), added to both `.env.example` and `docker-compose.yml`. No other service mounts it.
2. **Code talks to a small `FileStorage` interface, never to the filesystem directly.** It stores bytes, opens them and deletes them by key. `LocalFileStorage` implements it on a directory. Tests use a temporary directory, never the dev volume. A later S3 adapter (AWS S3, Cloudflare R2, SeaweedFS) can be added without touching services or routers.
3. **Storage keys are generated by the server** as `<purpose>/<uuid4>` (e.g. `resumes/3f2c…`). They are never derived from the uploaded file name, which is kept as metadata for display only. The adapter refuses any key that would resolve outside the storage root. This rules out path traversal and file-name collisions.
4. **MySQL holds the metadata**: file name, content type, size, storage key (`UNIQUE`) and upload time, like `submission_attachment`.
5. **Write order keeps the database honest.** A crash can leave an orphaned file, but never a row pointing at a missing file:
   1. write the new file under a fresh key;
   2. commit the database row (if the commit fails, delete the new file);
   3. only then delete the replaced file (a failure here is logged, and the file is an orphan).
6. **Downloads are streamed by the API** with access checks on every request, `Content-Disposition: attachment`, the stored content type and `X-Content-Type-Options: nosniff`. There are no public or presigned URLs.
7. **The image prepares the mount point.** The API Dockerfile creates `/app/storage` owned by the non-root `app` user before `USER app`, so a freshly created volume inherits that ownership and the API can write to it without running as root.

## Consequences

- **Reset and backups:**
  - `make reset-db` must also remove the `grow8_file_storage` volume, so files and metadata are wiped together.
  - A backup is MySQL **plus** this volume; one without the other leaves broken or orphaned references.
- **Scaling:** this works for **one API instance**. Running several replicas, or a host whose disk isn't persistent, is the trigger to add the S3 adapter (or mount a shared filesystem). Nothing else in the design blocks that switch.
- **Orphans:** files whose rows are gone are possible after crashes. A cleanup job that deletes keys not referenced in MySQL is future work and isn't needed at this scale.
- **Limits:** upload size limits are enforced by the API, so the whole file never has to be held in memory at once, and files go through Python rather than a CDN. That is acceptable for a few-MB cap.
- **Reuse:** work-submission attachments will reuse the same interface and volume under the `attachments/` prefix.
- **Tests:** a fixture points `FILE_STORAGE_DIR` at a temporary directory, so tests never touch the dev volume.
- The open question of where uploaded files are stored is closed by this ADR.
